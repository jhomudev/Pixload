## Specs
S1. User: "no hay otras mejoras posibles mas respecto al rendimiento?"; survey of remaining performance work, grounded in code and measurements, not generic advice.
S2. User: "inicia tal como tu recomendacion."; implement in the recommended order: (1) batched gallery validation, (2) cover thumbnail variant, (3) overlapped GIF pipeline. MediaCodec MP4 remains a separate project and is not implemented here.
S3. Batched gallery validation keeps identical availability semantics: a deleted entry is hidden, a permission or provider failure never hides an entry, and an entry without a stored tree URI keeps the per-entry query. One child listing per tree replaces one SAF query per entry, with a per-entry fallback only for entries missing from the listing.
S4. Cover thumbnail prefers Pixiv's `small` URL for the work cover (the card is 190 dp and page thumbnails already use `small`), falling back to `regular`, then to the novel `coverUrl`. No visual quality claim without a device check.
S5. GIF pipeline overlaps decoding and encoding without changing output bytes, delays, frame selection or cancellation. Measured against the recorded baseline on the same phone: 10 frames 2755 ms, 100 frames 21164 ms, PSS peak 170 MB (`docs/PERFORMANCE_MEASUREMENT.md`). S5 is refuted by L6: decoding is 0.6% of a conversion, so the overlap is worthless and was not implemented. Any replacement GIF optimization needs a new spec and explicit user authorization.

S6. User choice after L6, verbatim: "Pre-ditear fuera del encoder". Dither each frame outside `GifEncoder.addImage`, keeping pixels and delays identical; a permuted color-table order is acceptable. The vendored fast frame writer was explicitly not chosen.

L6. T3 measurement before writing code (temporary probes, deleted before commit; same phone, synthetic 480x270 JPEG ZIP, BALANCED preset, 30 frames, total 6563 ms = 219 ms/frame): JPEG decode plus `getPixels` 37 ms total (0.6%); `Image.fromRgb` raw pixels to Color grid ~350 ms (5%); `PaletteLookupDitherer` ~390 ms (6%); library `GifEncoder.addImage` on an already-dithered image, i.e. multiset, distinct scan, color-table index map, LZW and block writes 3976 ms (61%); our own int-keyed LZW over the same indices 595 ms (9%); Color-to-index map 479 ms (7%). The remaining gap is allocation pressure from the combined per-frame objects. So overlapping decode with encode would save at most 0.6% and was dropped. The real cost sits inside the third-party frame writer: `LzwEncoder.processIndex` copies a fresh `ArrayList` and hashes a `List<Integer>` per pixel, and `ColorTable`/`getIndices` are package-private, so nothing can be reused from our side. Two options were left to the user: pre-dither outside `addImage` (measured ~27-33% faster, no fork, palette order may permute while pixels and delays stay identical), or vendor a fast frame writer (projected ~5x, high risk, dependency-level change). Nothing implemented without authorization.
L7. T4 implemented. `PaletteLookupDitherer` now exposes `ditherPixels(pixels, width, height)` and shares one `ditherGrid` with `dither(Image, ...)`, and `GifConversion.convert` passes an already-dithered `Image` to `encoder.addImage`. The encoder only quantizes and dithers when the image has more than 256 distinct colors (`GifEncoder.addImage`), so a palette-only frame skips that block and nothing is dithered twice. Equivalence evidence: `PaletteDithererTest` (JVM) compares `ditherPixels` against `dither(Image.fromRgb(...))` — the previous path — pixel by pixel for all four diffuse/precise combinations plus a single-pixel frame; device `GifPixelSignatureProbeTest` (temporary, deleted) decoded the produced GIF and compared digests like for like: BALANCED baseline and change both `gifBytes=74860 pixelDigest=5056c7e4…`, FAST baseline and change both `gifBytes=48227 pixelDigest=0f4c2e55…`. `UgoiraConverterTest` needed only the pinned FAST byte hash updated (8092f76d… → 686d2788…); BALANCED kept `3a47b52a…`, which matches the accepted caveat that a permuted color-table order changes bytes while pixels and delays stay identical. A/B on the same phone, `GifPhase1BenchmarkTest`, 100 JPEG 480x270 frames, BALANCED, interleaved: cool baseline 20.4/19.9/21.8 s vs change 17.5/17.9 s; hot baseline 28.2/30.0 s vs change 24.7/24.4 s, so roughly 15% less time; peak PSS 148-162 MB → 92-94 MB and peak heap ~67-70 MB → ~32 MB, roughly 40% less memory. Suites on the final tree: app 123, shared 24, 0 failures; device `UgoiraConverterTest` OK (12 tests) and `GalleryDocumentsTest` OK (12 tests). Measured side finding, pre-existing and not caused by this change: `ArbitraryComparator` in the library keeps a static `WeakHashMap` of insertion-ordered ids, so a second conversion in the same process can order an equal-spread palette differently — the baseline reproduces it too (BALANCED digest `6f8265c3…` when FAST runs first).
