# MP4 conversion performance
Measure and reduce `UgoiraConverter.mp4` (JCodec) conversion work while preserving the playable output contract. Base: b165b85 (gallery work accepted); branch: feature/mp4-conversion-performance. Delivery: single-branch, ask before exceeding one coherent unit. No push/PR.
Runner: JDK 21 / SDK 35; app/shared JVM tests, debug APK builds, authorized-phone instrumentation with synthetic ugoira ZIPs.

## Specs
S1. User: "ya lo probé, funciona bien. Pasemos a lo siguiente. Delega a oh-my-pi las tareas y tu revisa todo." Delegate the authorized MP4 work to an interactive oh-my-pi agent in a new visible tab; the parent reviews and owns Git.
S2. Scope: MP4 conversion (`UgoiraConverter.mp4`, JCodec `AndroidSequenceEncoder`). GIF, gallery rendering, downloads, history and SAF code stay unchanged; no new dependencies.
S3. Measure a fresh device baseline before changing behavior, split it into decode/scale versus encode phases, and compare the same fixture after the change. Add runnable regression tests that pin the current MP4 contract first: playable output, duration, even dimensions, progress sequence, cancellation and the 10-minute limit. Report unavailable profiling explicitly.
S4. Preserve the observable output contract: MP4 container, H.264, 30 fps, at most 1280 px, even dimensions, same duration semantics, same error messages, same progress callbacks. Do not change resolution, frame rate, codec or file format without asking the parent; do not trade quality for speed silently.
S5. User: "Investigar MediaCodec (Recomendado)". Investigate and, if it measures well, implement an Android `MediaCodec` H.264 encoder with `MediaMuxer`, keeping JCodec as a fallback when hardware encoding is unavailable or fails, and preserving S4. No new dependencies. Prove the fallback path and compare against the retained JCodec baseline on the same fixture.
